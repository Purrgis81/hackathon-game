# hackathon-game
해커톤용 단기 게임 개발

## 침묵의 석실 · StoneChamber

Unity 3D 타일 회피 게임입니다. 혼자 플레이하거나 초대 코드로 2~4인 온라인 대전을 할 수 있습니다.

## 개발 환경

- Unity Editor **6000.3.13f1**
- Built-in Render Pipeline
- Unity Transport 2.7.5
- Multiplayer Services 2.5.0

## 프로젝트 실행

처음 Git을 사용하는 팀원은 아래 GitHub Desktop 순서로 진행하면 됩니다. 공개 저장소의 코드는 누구나 받을 수 있으며, 이 저장소에 직접 업로드할 팀원은 초대받은 GitHub 계정으로 협업 초대를 수락합니다.

### 1. 개발 도구 준비

- GitHub Desktop을 설치하고 본인의 GitHub 계정으로 로그인합니다.
- Unity Hub에서 Unity Editor **6000.3.13f1**을 설치합니다. Hub 목록에서 찾기 어려우면 Unity 다운로드 아카이브에서 해당 버전을 찾습니다.
- C#을 수정할 편집기인 Visual Studio 또는 Rider 등을 준비합니다.

[GitHub Desktop 다운로드](https://desktop.github.com/download/), [Unity Hub 다운로드](https://unity.com/download), [Unity Editor 아카이브](https://unity.com/releases/editor/archive)

### 2. 저장소 내려받기

1. GitHub Desktop에서 **File → Clone repository…**를 누릅니다.
2. **URL** 탭에 아래 주소를 입력합니다.
3. **Local Path**에서 프로젝트를 저장할 위치를 고르고 **Clone**을 누릅니다. 예를 들어 최종 폴더가 `D:\Projects\hackathon-game`이 되도록 지정할 수 있습니다.

```text
https://github.com/Purrgis81/hackathon-game.git
```

수정과 동기화를 이어갈 프로젝트는 이처럼 Clone으로 받습니다. 내려받은 폴더를 열면 `Assets`, `Packages`, `ProjectSettings`가 함께 있어야 합니다. [GitHub Desktop 클론 안내](https://docs.github.com/en/desktop/adding-and-cloning-repositories/cloning-and-forking-repositories-from-github-desktop)

### 3. Unity에서 실행

1. Unity Hub의 **Projects**에서 **Add / Add project from disk**로 기존 프로젝트를 추가합니다. 버튼 표기는 Hub 버전에 따라 조금 다를 수 있습니다.
2. 앞에서 클론한 `hackathon-game` 폴더 전체를 선택합니다. `Assets`, `Packages`, `ProjectSettings`가 들어 있는 상위 폴더입니다.
3. Unity **6000.3.13f1**로 열고 패키지 설치와 에셋 임포트가 끝날 때까지 기다립니다. 첫 실행에는 인터넷 연결이 필요합니다.
4. Unity의 Project 창에서 `Assets → Scenes → StoneChamber` 장면을 더블클릭합니다.
5. 상단 **▶ Play**를 누르고 **Game** 창을 클릭해 키 입력을 받습니다.

착지 연출 후 방향키 또는 WASD로 이동합니다. 첫발을 내딛기 전에 이름과 색상을 설정하거나 멀티플레이 방을 선택할 수 있습니다.

[Unity Hub 프로젝트 관리 안내](https://docs.unity.com/en-us/hub/projects)

## 멀티플레이

Windows에서 각자 다른 Steam 계정으로 로그인한 뒤 같은 버전의 게임을 실행합니다. 첫발을 내딛기 전에 **친구와 대전 → Steam → Steam 방 만들기**를 선택합니다. 방장은 **복사**로 방 코드를 공유하고, 참가자는 코드 전체를 붙여넣고 **Steam 코드로 참가**를 누릅니다. Steam Networking Sockets가 연결을 담당하고 방장 PC가 게임을 진행합니다. 테스트 App ID는 480(Spacewar)입니다. 테스트 ZIP을 통째로 풀고 실행 파일 옆에 steam_appid.txt를 유지하세요.

대기실에서 참가자가 **준비**를 누르면 발판 테두리가 회색에서 민트색으로 바뀌고 **준비 완료**가 표시됩니다. **준비 취소**를 누르면 다시 대기 상태가 됩니다. 금색 발판의 방장은 준비할 필요가 없습니다. 방장을 포함해 2~4명이 모이고 현재 참가자가 모두 준비하면 방장이 **게임 시작**을 누를 수 있습니다.

**기타 연결** 탭에서는 Unity Relay 방과 직접 IP 연결도 선택할 수 있습니다. Unity Cloud의 StoneChamber 프로젝트와 Relay가 연결되어 있습니다. 플레이어는 익명 인증으로 접속하며 게임 안에서 Unity 계정으로 로그인할 필요가 없습니다.

같은 네트워크에서는 IP 직접 접속도 지원합니다. 직접 접속 포트는 UDP 47737입니다. 모든 참가자는 같은 버전을 사용해야 합니다.

시뮬레이션은 120Hz입니다. 방장이 이동·점유·피격을 확정하며 참가자는 이동 예측과 보간을 사용합니다. 이동 데이터는 UDP로 전송하고, 방 구성과 시작 신호는 별도 신뢰성 채널로 전달합니다.

## 봇과 대전

첫 화면에서 **봇과 대전**을 누르면 인터넷 연결 없이 연습 대기실을 엽니다. 기본 봇 1명에 더해 **봇 추가**로 최대 3명까지 채울 수 있습니다. Steam·Relay·직접 연결 대기실에서도 방장이 빈자리에 봇을 추가할 수 있습니다. 사람이 참가하면 초과하는 봇부터 빠집니다. 사람과 봇을 합쳐 최대 4명이며, 사람 참가자는 기존처럼 준비를 눌러야 합니다.

봇 아래의 **성향**과 **난이도** 버튼을 각각 눌러 순환 선택한 뒤 **게임 시작**을 누릅니다. **봇 빼기**로 제거할 수 있습니다. 설정은 현재 방의 다음 라운드에도 유지됩니다.

- **생존형:** 안전한 자리와 탈출할 방향을 우선하며, 가까운 상대가 접근하면 현재 자리를 지켜 길을 막습니다.
- **견제형:** 두 칸 이내 상대의 이동 방향과 안전한 통로를 보고 길목을 적극적으로 선점합니다. 막은 자리가 안전하면 계속 유지합니다.
- **기회형:** 평소에는 조심스럽게 움직이고, 가까운 상대가 기절하면 견제 성향이 커집니다.
- **모험형:** 안전한 칸들 안에서 최근 방문하지 않은 위치와 새로운 경로를 탐색합니다. 상대의 길목을 일부러 선점하거나 붙어서 계속 막는 행동은 하지 않습니다. 옆에 함정이 있어도 다른 안전한 경로가 있으면 탐색하고, 이동할 안전한 칸이 없으면 기다립니다.
- **쉬움 / 보통 / 어려움:** 기본 판단 간격은 각각 약 0.50 / 0.21 / 0.13초이며, 봇마다 매 판단에 ±10% 변동을 줍니다. 이동 자체의 속도·피격 판정은 사람과 같습니다. 기절 해제도 간격을 둔 방향 입력 6회로 처리합니다.

**쉬움의 실수:** 실수 판정이 가능한 판단에서 20% 확률로 입력을 한 번 놓치거나 계획과 다른 방향을 고릅니다. 실수 바로 다음 판단은 정상 처리해 연속 실수를 막습니다. 다른 방향은 맵 밖·빈 발판·점유된 칸·이동 중 즉시 맞는 함정을 제외하지만, 먼 예고를 놓쳐 이후 위험해질 칸으로 갈 수 있습니다. 위험한 자리에서 멈칫해 탈출이 늦거나 블로킹을 풀기도 합니다. 따라서 전체 판단 중 실수 비율은 20%보다 낮고, 실수가 항상 사망으로 이어지지는 않습니다. 보통·어려움에는 이 실수를 적용하지 않습니다.

봇은 최근 상대의 이동 습관을 잠깐 기억하고, 최근 방문 칸과 즉시 되돌아가는 경로에 불이익을 줍니다. 자신의 위치가 위험하거나 탈출로가 부족하면 공격성을 낮춥니다. 안전한 행동끼리의 선택에는 봇 전용 난수를 사용해 반복을 줄이며, 게임의 패턴 난수에는 영향을 주지 않습니다. 새 라운드에서는 짧은 기억을 비웁니다.

위험 예측에는 공개된 가시·화살·독·파도·용암 예고와 발판 붕괴·균열 지대를 사용합니다. 화살의 한 줄 안전지대도 실제 발사 궤적으로 판별합니다. 균열 지대에서는 예고된 발판의 소멸 시각을 보고 대피하며, 이동이 끝나기 전에 출발 칸이나 도착 칸이 사라지는 경우도 위험으로 처리합니다. 사라진 발판은 경로에서 제외하고 실제로 복구되면 다시 이용합니다. 배속에 따른 균열·복구 시간도 실제 패턴과 함께 바뀝니다.

아직 드러나지 않은 다음 패턴이나 상대의 미입력 명령은 읽지 않습니다. 기존 함정의 배치·순서가 달라지는 패턴은 같은 위험 정보를 이용하지만, 새로운 종류의 함정은 `ChamberGame.Bots.cs`에 공개된 예고와 실제 충돌·소멸 규칙을 연결해야 합니다. 모든 공격을 피하는 무적 봇은 아닙니다. 봇은 게임 안의 규칙과 제한된 경로 탐색으로 동작합니다. 외부 AI API·모델·Node.js·API 키 설정은 사용하지 않습니다.

**안전구역 유지와 블로킹:** 정상 판단에서는 현재 칸이 안전하면 이동 중 피격되거나 도착 후 위험해질 칸으로 탐색·견제를 위해 들어가지 않습니다. 최소 1.2초와 현재 표시된 경고가 끝나는 시점까지 확인하며, 균열은 발판 소멸 시점까지 확인합니다. 생존형·견제형·기회형은 주변에 위험한 칸이 있으면 안전한 자리에서 기다리며, 모험형은 안전한 경로가 남아 있으면 그 안에서 탐색합니다. 새로운 예고가 현재 칸을 덮으면 대기를 취소하고 회피합니다. 쉬움의 실수로 인한 지연·예고 누락, 위험 예측 범위 밖의 공격이나 아직 공개되지 않은 공격까지 보장하는 기능은 아닙니다.

모험형을 제외한 봇은 두 칸 이내에 살아 있는 상대가 접근하면 현재 칸 또는 바로 옆의 안전한 칸을 이용해 통로를 막습니다. 상대가 이동 중이면 출발 칸과 도착 예정 칸을 모두 점유한 것으로 취급합니다. 블로킹은 일반 플레이어와 같은 칸 점유 규칙을 사용하며, 상대를 밀거나 입력을 읽지 않습니다. 견제형은 길목을 적극적으로 선점하고 생존형은 현재 안전한 자리에서 방어적으로 막습니다. 블로킹 자리도 위험해지면 회피가 우선합니다. 주변 위협이 사라지면 평소 탐색을 다시 시작합니다. 모험형도 칸을 점유하므로 지나가거나 안전한 자리에 대기할 때 우연히 상대의 길을 막을 수 있습니다.

온라인에서는 방장만 봇의 행동을 결정하고 기존 120Hz 입력 기록에 포함해 참가자에게 전달합니다. 5판 시상대와 봇을 함께 지원하는 버전은 네트워크 프로토콜 15를 사용하므로 모두 같은 빌드로 실행해야 합니다.

봇의 경로 판단은 쉬움·보통·어려움 순서로 현재 위치에서 최대 2·3·4칸 이내로 제한합니다. 각 첫 입력마다 유망한 경로 1·2·2개를 유지하면서 미래 2·6·10단계까지 살펴봅니다. 맵이 커져도 판단마다 탐색량에 상한이 있으며, 가시·독·용암은 실제 이동 구간에 닿을 수 있는 타일만 검사합니다. 균열 대상 목록도 같은 시뮬레이션 틱의 봇들이 함께 재사용하고, 각 경로에서는 출발·도착 칸만 확인합니다. 화살·파도처럼 움직이는 함정은 전체 이동 궤적과 충돌을 확인합니다.

성능 캡처는 **Window → Analysis → Profiler(Ctrl+7)**에서 **Play Mode**, **Deep Profile 끔**으로 녹화한 뒤 렉이 생긴 직후 정지하고 저장합니다. 저장한 `.data` 파일과 봇 수·난이도·맵 크기를 공유하면 됩니다. CPU Usage의 `ChamberBot.Decide` 표시는 봇의 판단 시간을 나타냅니다. `Tests/ChamberBotSmoke.cs`는 쉬움의 실수·성향·회피·탐색량 상한·충돌 예측·균열의 실제 낙하와 복구·한 줄 안전지대·호스트 입력 재생을 검증합니다. `Tests/ChamberBotPerformance.cs`는 균열 예고와 발판 소멸을 포함해 어려움 봇 3명이 동시에 판단하는 스트레스 테스트입니다. 두 파일은 격리한 프로젝트의 `Assets/Editor`에 복사해 각각 `ChamberBotSmoke.Begin`, `ChamberBotPerformance.Begin`을 배치 모드로 실행합니다.

## 현재 게임 규칙

- 발판은 10×10에서 시작해 3×3까지 줄어듭니다.
- 가시는 순차 전개, 양방향 나선, 전역 공격 패턴으로 나옵니다.
- 화살은 사방·팔방에서 시차를 두고 발사되며, 한 줄만 안전하게 남기는 패턴도 있습니다.
- 독은 짧게 남으며 십자·직선·별 패턴으로 퍼집니다.
- 파도는 캐릭터를 **그 파도와 같은 속도**로 가장자리까지 밀고 기절시킵니다. 파도 속도는 난이도에 따라 18~25유닛/초이며, 이동 도중 맞거나 다른 플레이어를 연쇄로 밀어도 해당 속도를 이어받습니다. 밀림·기절 중에도 가시·화살·독·용암에 피격됩니다. 같은 파도는 한 번만 밀림을 적용하며 새 파도는 다시 맞을 수 있습니다. 방향키 6회로 기절을 해제하고 입력이 없으면 4초 뒤 회복합니다. 회복 직후의 기존 0.65초 보호 시간은 유지합니다.
- 용암은 별도 공격 구간에서 2~4칸을 차례로 타격합니다.
- 균열 지대는 일부 발판을 예고한 뒤 깨뜨리고 잠시 후 복구합니다. 발판이 사라지는 순간 그 칸을 점유하면 낙하하며, 이동 중에는 출발 칸과 도착 칸을 모두 점유합니다.
- 상대가 점유한 칸은 막히며, 마지막 생존자가 라운드를 이깁니다.
- 친구 또는 봇과 5판을 마치면 해변 시상대가 열립니다. 총승수, 누적 생존 시간, 경기 시작 때 정한 추첨 순서로 순위를 매깁니다.

## 실시간 디버그 패널

Unity Editor의 Play 모드 또는 **Development Build**에서 **F1**이나 왼쪽 위 **디버그 열기** 버튼으로 패널을 엽니다. 착지 연출이 끝난 뒤 싱글플레이에서 사용할 수 있습니다. 멀티플레이 메뉴와 대전에서는 패널을 숨기고 조작을 차단합니다. 일반 배포 빌드에는 디버그 UI와 조작 API가 포함되지 않습니다.

- **맵 크기:** 3×3부터 10×10까지 즉시 변경합니다. 진행 중인 공격과 밀림·기절을 정리하며, 캐릭터를 현재 위치에서 가장 가까운 유효 칸에 배치합니다.
- **강제 패턴:** 가시 6종, 화살 8종(한 줄 안전지대 포함), 독 3종, 파도, 용암, 균열 지대, 발판 붕괴를 선택합니다. 기존 공격을 교체하고 선택한 패턴을 예고부터 실행합니다. 3×3에서는 추가 붕괴를 실행하지 않습니다.
- **자동 패턴 진행:** 기본으로 켜져 있으며, 맵 크기 변경·강제 패턴 실행·공격 지우기·테스트 초기화 후에도 선택한 상태를 유지합니다. 켜져 있으면 다음 일반 공격·균열 지대·붕괴를 계속 생성하며, 강제 실행한 패턴이 끝난 뒤에도 자동 진행합니다. 체크를 직접 끄면 현재 공격 종료 후 다음 패턴을 기다립니다. 꺼진 상태에서도 이동할 수 있습니다.
- **난이도:** 다음 패턴을 초반 0%, 중반 50%, 최대 100% 강도로 생성합니다. 진행 중인 공격의 수치는 변경하지 않습니다.
- **함정 발동 대기:** 슬라이더로 다음 패턴의 예고 시간을 **0.1~3.0초** 사이에서 0.1초 단위로 지정합니다. `1.0초 / 0.5초 / 0.1초` 버튼도 있습니다. 가시·화살·독·파도·용암·균열 지대 예고에 적용하며, 진행 중인 예고는 바꾸지 않습니다. 피할 칸에 독이나 용암이 남아 있으면 안전해질 때까지 예고가 연장될 수 있습니다. `자동`은 패턴별 기본 예고 시간과 3×3 자동 가속으로 복원합니다. 발판 붕괴 예고와 투사체 이동·피격 지속 시간은 이 설정으로 변경하지 않습니다.
- **3×3 자동 가속:** 3×3 진입 후 시뮬레이션 시간 60초에 걸쳐 함정 배속이 **1.0 → 1.5(30초) → 2.0배(60초)**로 증가합니다. 예고·연속 가시 간격·용암 연사 간격·패턴 사이 휴식 등을 단축하되, 예고 시간을 직접 지정하지 않은 경우 최소 0.6초를 보장합니다. 원래 0.6초보다 짧게 설정된 값은 그대로 유지합니다. 생존시간 카운터, 플레이어 이동, 화살·파도 이동 속도, 독·가시의 위험 지속 시간은 유지합니다. 패턴이 시작될 때 속도를 고정하므로 진행 중인 예고가 갑자기 짧아지지 않습니다. 맵 크기 변경 또는 라운드/테스트 초기화 시 가속 누적 시간을 초기화합니다.
- **함정 배속 조절:** 디버그의 배속 슬라이더와 `1.0배 / 1.5배 / 2.0배` 버튼으로 다음 패턴부터 적용할 배속을 0.1 단위로 지정합니다. 맵 크기와 관계없이 시험할 수 있고, 자동 패턴 진행의 켜짐/꺼짐 상태는 유지합니다. `자동`은 3×3에서 시간에 따라 가속하는 기본 동작으로 돌아갑니다. 아래의 **함정 발동 대기**에서 초를 직접 지정했다면 예고는 그 시간을 우선 사용하며, 연속 발동·휴식 간격에는 배속이 적용됩니다. 배속에 따른 최소 0.6초 예고를 확인하려면 발동 대기도 `자동`으로 두세요. 테스트 초기화는 선택한 배속을 유지하고, 일반 게임 복원은 수동 배속을 해제합니다.
- **공격 지우기 / 테스트 초기화:** 현재 공격만 정리하거나, 선택한 맵을 유지한 채 시간과 패턴 횟수를 초기화합니다. 사망 후에도 선택한 맵 크기를 유지합니다.
- **일반 게임 복원:** 10×10, 시간 기반 난이도, 자동 진행으로 되돌립니다. 디버그 조작을 한 테스트에서는 최고 생존 기록을 저장하지 않으며, 일반 게임 복원 후 새 기록 저장을 재개합니다.

## Two Color Cel 셰이더

캐릭터와 발판은 밝은 면과 그림자를 두 색으로 나누는 셀 셰이딩을 사용합니다. Flat Kit의 Two Color Cel 스타일을 참고한 자체 Built-in 셰이더이며, Flat Kit 패키지는 필요하지 않습니다. 캐릭터의 기존 텍스처·플레이어 구분색은 유지하고 픽셀 스냅과 UV 양자화를 제거했습니다. 공격 예고, 독, 파도, 용암의 전용 셰이더는 그대로 사용합니다.

- **캐릭터:** `Assets/Resources/ChamberAnimals`의 Bear, Rabbit, Frog, Cat 재질에서 `Stone Chamber/Two Color Cel`을 사용합니다.
- **발판:** `Assets/Resources/ChamberSlate.mat`을 조절합니다. 실행 시 `AbyssLighting`이 이 재질을 복제해 모든 발판에 적용하고, 플레이어 위치에 작은 빛 영역을 표시합니다.
- **Lit color / Shadow color:** 밝은 면과 어두운 면의 색입니다. 기본값은 캐릭터의 크림색 빛·푸른 그림자, 발판의 청회색 두 톤입니다.
- **Shadow size:** 값을 올리면 어두운 면이 넓어집니다. **Shadow edge softness**는 두 면의 경계를 부드럽게 만듭니다. 기본값은 각각 `0.35`, `0.015`입니다.
- **Texture strength:** `1`은 기존 동물 텍스처를 유지합니다. `0`은 텍스처를 빼고 두 색과 Tint만 사용합니다. **Cast shadow strength**로 다른 물체가 드리우는 그림자를 조절합니다.
- **Scene light color influence:** 기본값 `0`은 지정한 두 색을 유지합니다. 값을 올리면 주 광원의 색·세기를 반영합니다. 명암 방향과 실시간 그림자는 장면의 Directional Light를 따르며, 추가 Spot/Point Light와 환경광은 두 톤을 흐리지 않도록 제외합니다.

참고: [Flat Kit의 셀 셰이딩·텍스처 설정](https://flatkit.dustyroom.com/stylized-surface/). 원래 픽셀 셰이더 `ChamberPixels.shader`도 보관되어 있습니다.
## 함께 개발하기

아래는 기능별 브랜치에서 수정한 뒤 `main`에 합치는 권장 작업 흐름입니다. 브랜치는 각자의 작업 공간이고, Pull Request는 수정 내용을 함께 확인하고 합치는 요청입니다.

### 1. 작업 시작 전에 최신 코드 받기

1. 이전에 작업하던 내용이 있으면 Unity에서 저장하고 현재 작업 브랜치에 커밋합니다.
2. Unity 프로젝트를 닫은 상태에서 GitHub Desktop의 **Current Branch**를 `main`으로 선택합니다.
3. **Fetch origin**을 누르고, **Pull origin**이 나타나면 눌러 팀원들이 합친 최신 코드를 받습니다.
4. **Current Branch → New Branch**에서 이번 작업용 브랜치를 만듭니다. 예를 들어 `feature/lava-balance`, `feature/player-motion`, `fix/arrow-warning`처럼 작업 내용을 이름으로 씁니다.
5. 최신 `main`을 기준으로 브랜치를 만든 뒤 Unity 프로젝트를 다시 엽니다.

[브랜치 만들기](https://docs.github.com/en/desktop/making-changes-in-a-branch/managing-branches-in-github-desktop), [Fetch와 Pull 안내](https://docs.github.com/en/desktop/working-with-your-remote-repository-on-github-or-github-enterprise/syncing-your-branch-in-github-desktop)

### 2. Unity와 편집기에서 수정

1. Play를 끄고 C# 코드, 장면, 프리팹이나 에셋을 수정합니다.
2. 변경한 파일을 저장합니다. 장면은 **Ctrl+S**로 저장할 수 있습니다.
3. 게임 장면에서 Play를 눌러 동작을 확인하고 Console의 빨간 오류를 해결합니다.
4. 확인이 끝나면 Play를 끄고 **File → Save Project**로 프로젝트 설정을 저장합니다.

에셋을 추가하거나 옮기면 해당 `.meta` 파일도 함께 커밋합니다. 에셋 이동과 이름 변경은 Unity Editor에서 하면 참조를 보존하기 쉽습니다. 장면 파일은 텍스트 직렬화, 버전 관리는 Visible Meta Files로 설정되어 있습니다.

### 3. 수정 내용을 GitHub에 올리기

1. GitHub Desktop의 **Changes**에서 이번 작업에 해당하는 파일과 에셋의 `.meta`를 확인합니다.
2. **Summary**에 변경 내용을 적습니다. 예를 들어 `용암 예고 시간을 늘리고 타격 수 조정`처럼 씁니다.
3. **Commit to 작업브랜치**를 눌러 내 컴퓨터의 Git에 변경 이력을 저장합니다.
4. **Publish branch**를 눌러 새 브랜치를 처음 올립니다. 이미 올린 브랜치에는 **Push origin**을 눌러 후속 커밋을 전송합니다.
5. GitHub 저장소의 브랜치 목록에서 자신의 브랜치와 최신 커밋이 보이는지 확인합니다.

Commit은 로컬 이력 저장, Push는 GitHub 전송입니다. 두 단계를 마치면 다른 팀원도 해당 브랜치의 수정 내용을 받을 수 있습니다. Push 전에 Desktop이 Pull을 안내하면 원격 변경을 먼저 가져오고 충돌 여부를 확인합니다. [커밋 안내](https://docs.github.com/en/desktop/making-changes-in-a-branch/committing-and-reviewing-changes-to-your-project-in-github-desktop), [업로드 안내](https://docs.github.com/en/desktop/making-changes-in-a-branch/pushing-changes-to-github-from-github-desktop)

### 4. 팀의 main에 합치기

1. 업로드한 작업 브랜치에서 **Preview Pull Request → Create Pull Request**를 누릅니다. 브라우저에서 저장소의 **Pull requests → New pull request**로 시작해도 됩니다.
2. 합칠 대상인 **base**를 `main`, 변경 내용을 가져올 **compare**를 자신의 작업 브랜치로 선택합니다.
3. 제목과 설명에 무엇을 바꿨고 어떻게 테스트했는지 적고 Pull Request를 생성합니다.
4. 팀원이 변경 내용을 확인한 뒤 **Merge pull request**로 `main`에 합칩니다.
5. 각 팀원은 Unity 프로젝트를 저장하고 닫은 뒤 `main`으로 전환해 **Fetch origin → Pull origin**으로 합쳐진 내용을 받습니다.

[Pull Request 만들기](https://docs.github.com/en/desktop/working-with-your-remote-repository-on-github-or-github-enterprise/creating-an-issue-or-pull-request-from-github-desktop)

### 작업 중 main의 변경이 필요할 때

현재 작업을 커밋한 뒤 `main`으로 전환해 Fetch와 Pull을 합니다. 자신의 작업 브랜치로 돌아와 **Current Branch → Choose a branch to merge into…**에서 `main`을 골라 합칩니다. 충돌이 나타나면 겹친 파일을 수정한 팀원과 두 변경을 확인하고, 해결한 결과를 커밋합니다.

같은 장면이나 프리팹을 함께 수정할 때는 작업 범위를 먼저 공유하면 충돌을 줄일 수 있습니다. 네트워크 메시지나 판정을 바꾸면 같은 버전의 클라이언트 여러 개로 함께 검증합니다.

### 문제가 생겼을 때

| 증상 | 확인할 내용 |
| --- | --- |
| 업로드에서 권한 오류가 남 | GitHub Desktop의 로그인 계정과 협업 초대 수락 여부를 확인합니다. 공개 저장소도 직접 Push하려면 쓰기 권한이 필요합니다. |
| Unity Hub가 프로젝트를 인식하지 못함 | 선택한 폴더 바로 아래에 `Assets`, `Packages`, `ProjectSettings`가 있는지 확인합니다. |
| 장면이 비어 있거나 다른 화면이 나옴 | `Assets/Scenes/StoneChamber.unity`를 엽니다. |
| C# 컴파일 오류가 남 | Console의 첫 번째 빨간 오류를 확인합니다. 사용 중인 Unity 버전과 최근 수정 파일을 함께 확인합니다. |
| Pull 또는 병합에서 충돌이 남 | 현재 변경을 저장·커밋한 상태에서 겹친 내용을 확인하고 해결합니다. 충돌 해결 후 다시 게임을 실행해 확인합니다. |

Unity가 생성하는 캐시·로그·개인 설정과 실행 빌드는 Git에서 제외됩니다. 임포트에 필요한 소스 에셋과 패키지 잠금 파일은 포함됩니다.
